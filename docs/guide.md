# 進め方

意思決定を中心にプロジェクトを進めるための、記録の形と回し方。作業の量ではなく、決めるべきことが決まったかで進捗を測る。

## 考え方

- **進捗は、確定した決定の割合で測る。** 成果物（WBS）ごとに「決めること（問い）」を起票し、問いがすべて確定したら、その成果物は完成とする。
- **AIは提案し、人間が決める。** AIは選択肢、反論、見落としを出す。決めるのは人間で、誰が決め、誰が記録したかを残す。
- **記録は追記だけ。** 確定した記録は書き換えない。覆すときは新しい記録を作る。手戻りは、記録の書き換えではなく、新しい記録の追加として見える。
- **タスクは決定から派生させる。** タスクは決定記録の外（`tasks.csv`）に置き、必ず元の決定を指す。期限は問いに置き、担当や期限の管理は外部のタスク管理に任せる。タスクの管理そのものを中心にしない。中心にすると、作業の消化を進捗とする、ふつうのタスク管理に戻ってしまうため。

## サイクル

1. **問いを起票する**：決めるべきことが生じたら、`project/decisions/_template.md` を写して `dr-NNNN.md` を作り、`status: open` で起票する。
2. **選択肢と根拠を集める**：AIが選択肢・反論・見落としを出し、人間が妥当性を確かめる。疑問は、決める前に対話で確かめる。
3. **決める**：人間が選び、理由を書く。`status: decided`、`decided_at`、`decided_by`、`recorded_by`（記録した人と決めた人が違えば `evidence` も）、AIの推奨とそれに従ったかを書く。
4. **タスクを起こす**：決定を実行するタスクを `project/tasks.csv` に足す。`dr` に元の決定を書く。
5. **結果を記録する**：タスクが終わったら、`result` と `result_ref` を書く。結果が前提を崩したら、新しい問いを起票する（1に戻る）。
6. **ゲートを通る**：ゲートの当日に、まとめを作り、判断を決定記録で確定する（下の「ゲート」）。
7. **レポートを作る**：`python3 tools/report.py --derive` をAIに渡して判断の欄を書かせ、`python3 tools/report.py` で作る。人間が読み、確認したら `confirmed_by` を書く。
8. **セッションを記録する**：`project/sessions/` に、その回の問い、決定、生まれた成果物とタスクを残す。

## ファイル

すべて `project/` の中。`examples/sample-project/` に、架空の例がある。

| ファイル | 内容 | 書く人 |
| --- | --- | --- |
| `decisions/dr-NNNN.md` | 決定記録（1件1ファイル） | 人間とAI。確定は人間の回答に基づく |
| `decisions/index.csv` | 決定記録の一覧 | 生成（`tools/build_index.py`） |
| `tasks.csv` | 決定から派生したタスクと、その実行結果 | 人間とAI |
| `wbs.csv` | 成果物WBS（成果物、状態、決めること、ファイル）。決定記録の `wbs`・`affects` はこの番号を指す | 人間とAI |
| `plan.json` | 完成の期限と範囲、作業の余力、ゲート、壁（QCD） | 人間（AIは案を出す） |
| `gates/<ゲートID>.md` | ゲートのまとめ | 下書きは生成（`tools/gate.py`）。AIが埋め、人間が確かめる |
| `judgments.json` | レポートの判断の欄 | AIが提案し、人間が確認する |
| `report/` | レポート（`report.json`、`report.html`） | 生成（`tools/report.py`） |
| `sessions/` | セッションの記録 | 人間とAI |

### 決定記録の項目

| 項目 | 内容 |
| --- | --- |
| id | DR-NNNN（連番。ファイル名 `dr-NNNN.md` と一致させる） |
| title | 問いを一文で。決定後は結論を一文で |
| wbs | 関係する成果物のWBS番号（`wbs.csv` にあること） |
| category | management / design / evaluation |
| status | open / decided / superseded |
| owner | 決める人の役割 |
| due | 決める期限 |
| decided_at、decided_by | 決めた日と、決めた人の役割（人間） |
| recorded_by | 記録した人の役割、またはAIエージェントの名前 |
| evidence | 承認の根拠の場所。記録した人と決めた人が違うときは必須 |
| supersedes | この記録が覆す前の記録のID |
| affects | 影響する成果物のWBS番号（`wbs.csv` にあること）。文書はWBSの `file` 列でたどる |
| ai_recommended | AIが推奨した選択肢。なければ none |
| followed_recommendation | 推奨どおりに決めたか（true / false） |
| dialogue_before | 決める前に、AIとの対話で疑問を確かめたか（true / false） |
| verify_at | 決定の結果を確かめる時期（日付、またはゲートのID）。任意 |

本文は「背景」「選択肢」「決定と理由」、任意で「期待」（決定の時点で何を期待したか）。

`ai_recommended`、`followed_recommendation`、`dialogue_before` は、AIの推奨を人間が考えずに追認していないかを、後から測るための項目である。

### タスクの項目

| 項目 | 内容 |
| --- | --- |
| id | T-NNNN |
| title | タスク |
| dr | 元の決定記録（必須） |
| status | todo / doing / done / dropped |
| result | 結果を一文で（done のとき必須）。やめた理由（dropped のとき必須） |
| result_ref | 結果の場所：コミット、PR、ファイル（done のとき必須） |
| ref | 外部のタスク管理での場所（GitHub Issues など）。任意 |

tasks.csv はタスク管理ではなく、**決定と結果をつなぐ台帳**である。担当、期限、細かい進み具合は、外部のタスク管理（GitHub Issues、Planner など）に任せ、`ref` でつなぐ。期限は、タスクではなく、それが答える問い（決定記録の `due`）に置く。レポートとゲートのまとめは、未決の問いごとに、それを進めているタスクを並べて見せる。

## ゲート

`plan.json` の `gates` に、期日、通過の条件、状態（未 ／ 通過 ／ 範囲を絞って通過 ／ 通過しない）を置く。ゲートでは、条件を満たしているかを人間が確かめ、足りなければ範囲を絞る。品質の壁は動かさない。壁を動かすときは、決定記録で決める。

ゲートごとに、`gates/<ゲートID>.md` にまとめを残す。

1. **下書きを作る**：ゲートの当日に `python3 tools/gate.py --gate <ゲートID>` を実行する。1章（その時点の数字）は導出値から書かれる。手で直さない。
2. **埋める**：AIが、2章（条件ごとの確認と根拠）、3章（`verify_at` がこのゲートの決定について、期待どおりだったかの照合）、5章（判断の案）を下書きし、人間が確かめる。
3. **決める**：判断を決定記録で確定し、まとめの「判断の決定記録」の行に、そのIDを書く。
4. **状態を変える**：`plan.json` のゲートの `status` を変え、レポートを作り直す。

`status` が「未」以外のゲートに、まとめと、確定した判断の決定記録がなければ、`tools/validate.py` がエラーにする。例は `examples/sample-project/gates/G1.md`。

ゲートの運用は、元になったプロジェクトでも一巡していない。使ってみた結果で見直す。

## スプリント

スプリントを、期限・範囲・終わりの判定を持つ小さなプロジェクトとして回す。決定記録の台帳は1本のまま、スプリントで絞って見る。

### 計画

`plan.json` に `sprints` を置く。`sprints` がない、または空なら、道具は元のテンプレートと同じに動く。

```json
"sprints": [
  {"id": "S1", "goal": "スプリントゴール", "start": "2026-11-02", "end": "2026-11-13", "status": "未"}
]
```

| 項目 | 内容 |
| --- | --- |
| id | スプリントのID。ゲートのIDと重ねない |
| goal | スプリントゴール。レビューの条件になる |
| start、end | 期間（両端を含む）。ほかのスプリントと重ねない |
| status | 未 ／ 達成 ／ 一部達成 ／ 未達成（レビューの結果） |

完成の定義（DoD）は、品質の壁（`walls.quality`）に書く。リリース判定など、スプリントをまたぐ区切りは、これまでどおり `gates` に置く。

### 所属

| 記録 | 属するスプリント |
| --- | --- |
| 確定・覆された決定 | `decided_at` が期間に入るスプリント |
| 未決の問い | `due` が期間に入るスプリント（期限を動かせば、所属も動く） |
| タスク | `tasks.csv` の `sprint` 列（任意。空なら、どのスプリントにも属さない） |

決定記録にスプリントの項目は書かない。日付から道具が導出する。

### 回し方

1. **計画**：スプリントの初日に、`sprints` にゴールと期間を足す。このスプリントで決める問いの `due` を期間の中に置き、タスクの `sprint` を書く。
2. **進める**：サイクル（上の1〜8）を、これまでどおり回す。
3. **レビュー**：最終日に `python3 tools/gate.py --gate S1` でまとめの下書きを作る。条件はスプリントゴールで、1章に、そのスプリントの数字が入る。達成したかを決定記録で確定し、まとめの「判断の決定記録」にIDを書き、`sprints` の `status` を変える。
4. **振り返り**：進め方を変えるなら、決定記録（WBSの進め方）にする。

### レポート

- `python3 tools/report.py`：`as_of` を含むスプリントを「今のスプリント」として、その節（ゴール、確定した決定、未決の問い、タスク）と、スプリントの一覧と、台帳全体の数字を出す。
- `python3 tools/report.py --sprint S1`：S1 を今のスプリントとして、`report/report-S1.json`、`report-S1.html` に書く。判断の欄は今の時点の評価なので、載せない。
- 判断の欄で今のスプリントの件数を書くときは、次の言い回しにする（道具が照合する）：「このスプリントで確定した決定がN件」「このスプリントの未決の問いがN件」「このスプリントの残りのタスクがN件」。

例は `examples/agile-sample/`（架空）。

## Git以外の置き場

正本はGit（とCI）に置く。Microsoft 365 で回す手順は `adapters/copilot-studio/README.md`。

## このテンプレートの由来

設計中のプロジェクトマネジメントツール（決定と承認の台帳を正本に、因果構造で不確実性を収束させるもの）の開発の進め方を、ほかのプロジェクトで使えるように切り出した。決定記録の項目は、そのツールの決定ノードの属性に揃えてあり、将来、ツールとの取り込み・書き出しでつなぐことを検討している。
